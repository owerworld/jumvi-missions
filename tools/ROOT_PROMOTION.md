# Root promotion, 2026-10-05

Human authorization is recorded in artifacts/root-promotion-approval.json. Root (`/`, `/tr/`) renders the current reviewed V2 using immutable `/v2/releases/...` resources and the existing `jumvi-v2:` IndexedDB/local storage namespace. It does not copy, infer, or merge legacy progress. `/v2/` and `/v2/tr/` remain usable. Root PWA manifest uses `/` identity/start/scope; installed `/v2/` remains `/v2/`.

The archived exact legacy shell is available at `/v1/` and `/v1/tr/`. Only manifest and SW registration paths are adapted. Static assets continue at their original public paths. The V1 worker has `/v1/` scope and `jumvi-v1-legacy-` cache ownership; it cannot delete V2/home caches. Root uses `jumvi-home-`, V2 uses `jumvi-v2-`. New SWs do not force activation or take over open rounds. Existing root clients can receive the new shell online while the replacement waits safely. No general cache/IndexedDB/localStorage clearing occurs. Existing old root data remains available to V1, using the original keys.

`tools/build-root-promotion.mjs` consumes exact built V2 plus pinned archived legacy bytes. It never fetches production data. Root gateway forwards unchanged admin/API/static paths to the existing same-host Custom Domain origin; staging substitutes allowlisted local public files and blocks privileged paths. `jumvi-missions` Worker/version/domain remains intact. `jumvi-v2-legacy-compat` gains only the authorized qr.jumvi.co wildcard route; the more-specific V2 route continues to use its existing Worker. No changes on jumvi.co/www.

ROOT_EXACT_SHA and ROOT_EXACT_ARTIFACT pins must match the branch and the isolated staging manifest. ROOT_STAGING_VERIFIED_SHA is set only after successful root-promotion staging workflow and hosted verification. `root-promotion.yml` publish rebuilds and validates staging again, publishes V2 assets first, then the entry router, then checks live hashes and flows. Existing V2-only release and ordinary staging workflows are held when ROOT_PROMOTION_ACTIVE=true, avoiding accidental replacement of the promoted router with the old SW-only compatibility Worker.

Automatic rollback on a publication/post-verification failure uses a separate CI worktree at the pinned pre-promotion c71cd2d commit, redeploying its compatibility route (service-worker.js only) and exact V2 artifact. Removing the promoted wildcard returns root directly to the preserved Custom Domain Worker. No database rollback or data deletion. The flag remains held after rollback until the operator records the outcome; do not reenable an old automatic publisher blindly. Rollback local transition is tested; physical-device recovery is not claimed.

The old site may retain legacy copy/mechanics/features; moving it is not a new content acceptance. Watermark, public-source/privacy blockers and analytics-disabled state remain as previously recorded. Do not label this migration new physical-phone QA or blanket M6 PASS.
